# `$IO`: что именно отличается от нужного

Сравнение прочитано глазами по двум полным листингам, а не выведено из
статистики. Смещения даны **от начала модуля**.

* `IO-ours.asm` — наш `$IO` из `MIXT.SAV`, база `006376`, размер `0o2704` (1476 б)
* `IO-tetris.asm` — `$IO` внутри `TETRIS.SAV`, база `024260`, размер `0o2674` (1468 б)

Разница размеров — **8 байт**. Ниже показано, что все восемь объясняются
тремя правками, и ничем больше.

---

## Сначала о том, что различием НЕ является

### Дескрипторы ошибок

По восьми местам модуля стоит вызов `JSR R0,$ERROR`, за которым **встроенные
данные**: байт класса, байт номера, слово длины, текст. Дизассемблер честно
показывает их как команды — читать надо по текстовой колонке.

```
        наш                                тетрис
+0150   JSR R0,$ERROR                      JSR R0,$ERROR
+0154   000000  <- класс 0, номер 0        017000  <- класс 0, номер 0x0E = 30
+0156   000015  <- длина 13                000015
+0160   "FILE NOT OPEN"                    "FILE NOT OPEN"
```

Все восемь:

| смещение | сообщение | наш номер | в тетрисе |
|---|---|---|---|
| `+0154` | `FILE NOT OPEN` | 0 | 30 |
| `+0242` | `CAN'T READ` | 0 | 18 |
| `+0272` | `END OF FILE` | 0 | 17 |
| `+0464` | `PUT NOT ALLOWED` | 0 | 19 |
| `+0762` | `FILE OVERFLOW` | 0 | 33 |
| `+2364` | `TRANSFER ERROR` | 0 | 33 |
| `+2412` | `CHANNEL NOT OPEN` | 0 | 30 |
| `+2442` | `WRITE PAST EOF` | 0 | 33 |

Это **данные**, а не код: длина модуля от них не меняется, поведение тоже —
штатный обработчик `ERROR.PAS` принимает номер параметром `ERRORNUMBER` и не
использует его (проверено запуском: программа с делением на ноль печатает
`?FATAL ERROR: DIVISION BY ZERO` без номера).

### Разъехавшиеся адреса переходов

После первой же правки все последующие `Bxx` и `JSR` смещаются на 2, потом на
8. Считать это различием нельзя — это следствие, а не причина.

---

## Правка 1. Лишняя проверка на ноль, `+0620` (−2 байта)

Подпрограмма `L17` пересчитывает позицию в буфере.

```
        наш                                    тетрис
+0574   L17: ADD 26(R5),-(R5)                  L17: ADD 26(R5),-(R5)
+0600        MOV (R5)+,R0                           MOV (R5)+,R0
+0602        BIT #2,(R5)                            BIT #2,(R5)
+0606        BNE L19                                BNE L19
+0610        SUB 20(R5),R0                          SUB 20(R5),R0
+0614        BIC #177000,R0                         BIC #177000,R0
+0620        BEQ L18            <<< ЛИШНЕЕ      ---
+0622        ADD 26(R5),R0                          ADD 26(R5),R0      (+0620)
+0626        SUB #1000,R0                           SUB #1000,R0       (+0624)
+0632        BLOS L18                               BLOS L18           (+0630)
+0634        SUB 26(R5),R0                          SUB 26(R5),R0      (+0632)
+0640        SUB R0,177776(R5)                      SUB R0,177776(R5)  (+0636)
+0644   L18: MOV 177776(R5),R0                 L18: MOV 177776(R5),R0  (+0642)
```

**Смысл.** У нас: если после `BIC #177000` остаток нулевой (позиция ровно на
границе блока), пересчёт пропускается. В нужной сборке этой проверки нет, путь
всегда полный — `BLOS L18` ниже ловит тот же случай.

**Что делать:** удалить слово `001411` (`BEQ`) по смещению `+0620`.

## Правка 2. Маска в `BIT`, `+1150` (0 байт)

```
        наш                                    тетрис
+1142   MOV 20(R5),-(R5)                       MOV 20(R5),-(R5)      (+1140)
+1146   MOV (R5)+,30(R5)                       MOV (R5)+,30(R5)      (+1144)
+1150   BIT #14,(R5)       <<<                 BIT #10,(R5)          (+1146)
+1154   BEQ L28                                BEQ L28
+1156   JSR PC,L49                             JSR PC,L49
```

**Смысл.** Слово состояния файлового блока. У нас проверяются два бита
(`0o4` и `0o10`), в нужной сборке только `0o10`. То есть у нас `L49` (сброс
буфера на устройство) вызывается ещё в одном случае.

Обратите внимание: такой же `BIT #14,(R5)` есть в обоих по смещению `+1116` —
там маска совпадает. Отличается только это, второе вхождение.

**Что делать:** заменить операнд `000014` на `000010` по смещению `+1152`.

---

## Правка 3. Дозапись нечётного байта, `+2610` (−6 байт)

Формирование блока запроса для `EMT 375` (`.WRITW`).

```
        наш                                    тетрис
+2600   CMPB 14(R5),#377                       CMPB 14(R5),#377      (+2576)
+2606   BEQ L67                                BEQ L66               (+2604)
+2610   INC R1             <<<                 MOV #<буфер>,R2       (+2606)
+2612   ASR R1             <<<                 MOVB 14(R5),(R2)+     (+2612)
+2614   BCS L66            <<< УДАЛИТЬ         MOVB #11,(R2)+        (+2616)
+2616   CLRB @30(R5)       <<< УДАЛИТЬ         MOV 16(R5),(R2)+      (+2622)
+2622   MOV #<буфер>,R2                        MOV 20(R5),(R2)+      (+2626)
+2626   MOVB 14(R5),(R2)+                      INC R1                (+2632) <<< ПЕРЕНЕСЕНО
+2632   MOVB #11,(R2)+                         ASR R1                (+2634) <<< ПЕРЕНЕСЕНО
+2636   MOV 16(R5),(R2)+                       MOV R1,(R2)+          (+2636)
+2642   MOV 20(R5),(R2)+                       CLR (R2)+             (+2640)
+2646   MOV R1,(R2)+                           MOV #<буфер>,R0       (+2642)
+2650   CLR (R2)+                              EMT 375               (+2646)
+2652   MOV #<буфер>,R0                        BCS L56               (+2650)
+2656   EMT 375                                BR L61                (+2652)
```

**Смысл.** `INC R1` + `ASR R1` — перевод счётчика байт в счётчик слов с
округлением вверх. У нас перед этим ещё и обнуляется «хвостовой» байт, если
длина нечётная (`BCS` → `CLRB @30(R5)`); в нужной сборке этого нет, а сам
пересчёт передвинут ниже, к месту, где значение кладётся в блок запроса.

**Что делать:** удалить `BCS` (`103402`) и `CLRB @30(R5)` (`105075 000030`),
а пару `INC R1` / `ASR R1` перенести на четыре команды ниже.

---

## Сходится ли счёт

| правка | байт |
|---|---|
| 1. убрать `BEQ` | −2 |
| 2. поменять маску | 0 |
| 3. убрать `BCS` и `CLRB`, перенести `INC`/`ASR` | −6 |
| **итого** | **−8** |

`0o2704 − 8 = 0o2674` — ровно размер `$IO` в тетрисе. Значит список правок
**исчерпывающий**: ничего не пропущено и ничего лишнего.

## Проверка: сделана, сошлось в ноль

`tools/iopatch.py` применяет правки к образу модуля механически и сверяет
результат с тем, что лежит в `TETRIS.SAV`.

Удаление байт сдвигает всё, что ниже, поэтому мало вырезать куски: у каждого
условного перехода, `SOB` и операнда в режиме «относительно PC» цель уезжает, и
смещение надо пересчитать. Границы команд берутся из листинга SIMH, а не
угадываются. Непосредственные операнды (`#константа`) при этом трогать нельзя —
они не смещения.

```
$ ./tools/iopatch.py pascal/rebuild/IO-ours.asm pascal/rebuild/MIXT.SAV 6376 \
                     tetris/dis/TETRISB.SAV 24260 2674
исходный 1476 б -> после правок 1468 б;  нужно 1468 б;  пересчитано переходов: 12
расхождений после правок: 0  (в релоцируемых словах: 91)
```

**Ноль расхождений.** Наш `$IO` плюс три правки кода и восемь байтов номеров
ошибок даёт ровно то, что внутри тетриса. Оставшийся 91 байт — слова, которые
подставляет компоновщик; они и должны отличаться.

По дороге проверка поймала мою недоделку: сначала пересчитывались только
условные переходы, и осталось семь расхождений — смещения `JSR PC,X(PC)`.
После того как пересчёт распространили на все PC-относительные операнды,
осталось ровно восемь байтов номеров, а с ними — ноль.

Это доказывает, что список правок **полон**: если бы существовала четвёртая,
она бы здесь и всплыла.
